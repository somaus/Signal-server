# 위험도 분석 (측정 기반, `risk-analysis.mode=http`)

사진 위험도 진단에는 두 가지 방식이 있다. 기본값은 기존 방식(`llm`)이고, `http`는 직접 만든 측정 파이프라인이다.

| | `llm` (기본) | `http` |
|---|---|---|
| 얼굴 위치 | 비전 LLM이 말한 좌표(추정) | YuNet 얼굴 검출 모델, 얼굴 여러 명 모두 |
| 이미지 품질 점수 | LLM이 정한 숫자 | 얼굴 픽셀 크기와 선명도를 잰 값으로 계산 |
| 얼굴 노출도 점수 | LLM이 정한 숫자 | 얼굴 면적 비율과 정면도를 잰 값으로 계산 |
| 메타데이터 노출 | EXIF를 직접 읽음(동일) | 동일 |
| 역검색 노출 위험 | LLM의 추정 | 항목에서 뺌(실제 역검색 없이는 잴 수 없다) |
| 같은 사진을 다시 분석 | 결과가 달라질 수 있음 | 항상 같음(5회 반복해 동일 확인) |
| 읽을 수 없는 이미지, 해상도·용량 초과 | 서버 오류로 처리 | 거절 사유를 구분(실패 사유 `INVALID_IMAGE`, 다시 시도해도 같음). 서버 오류·바쁨은 `AI_SERVER_ERROR` |
| 외부 호출 | Groq(사진이 외부로 전송됨) | 내부 risk-lab 서비스만(사진이 밖으로 나가지 않음) |

## 구성

`risk-lab`(FastAPI + OpenCV, `risk-lab/README.md`)이 얼굴 검출과 측정을 하고, 서버의 `HttpRiskAnalyzer`가 `RiskScoring`의 고정 공식으로 점수를 만든다. 설명 문구에는 점수의 근거가 된 측정값(얼굴 한 변 px, 화면 대비 %, 선명도, 정면도)이 그대로 들어간다. 측정 서비스가 실패하거나 시간 초과면 임의 점수를 만들지 않고 "분석하지 못함"으로 응답한다.

## 점수 공식 (`RiskScoring`)

- 이미지 품질 = 0.6 x 해상도 + 0.4 x 선명도. 해상도는 얼굴 짧은 변이 48px 이하면 0, 256px 이상이면 1(로그 눈금). 선명도는 라플라시안 분산 15 이하 0, 300 이상 1.
- 얼굴 노출도 = 0.5 x 면적 + 0.5 x 정면도. 면적은 얼굴이 이미지의 0.5% 이하면 0, 15% 이상이면 1(로그 눈금). 정면도는 코끝이 두 눈 중앙에서 벗어난 정도(1이 정면).
- 여러 명이면 항목별로 가장 높은 얼굴 기준.
- 종합 점수 = 품질 40% + 노출도 40% + 메타데이터 20%. 등급 경계는 기존과 같다(40, 70). 단순 평균이면 위치 정보(GPS)가 없을 때(메타데이터 고정 10점) 품질과 노출도가 둘 다 100이어도 70이 한계라 높음에 거의 닿지 못해서 가중 합으로 바꿨다. GPS가 없을 때 두 항목이 모두 85 이상이면 높음이다.

**한계(중요).** 측정값은 실제로 잰 값이지만, 위 경계값은 "합성 재료로 쓰기 좋은 사진의 조건"을 생각해 정한 값이다. 실제 악용 사례나 사용자 라벨로 검증한 위험 모델이 아니고, 피해가 날 확률도 아니다. 검증하려면 위험 정도를 사람이 매긴 사진 세트가 필요한데 지금은 없다. 그래서 이전 방식(LLM)과의 정확도 비교는 하지 못했다(정답이 없고, 이 환경에서 Groq에 닿지 않는다).

## 자원과 한계값

- 해상도 상한 4천만 화소(`RISK_MAX_PIXELS`), 용량 15MB. 넘으면 413. 디코딩 직후 긴 변 2048px 이하로 줄여 검출·측정하고(JPEG는 디코딩 단계에서 줄여 읽는다), 박스와 얼굴 픽셀 수는 원본 기준으로 되돌려 낸다.
- 최대 메모리를 4천만 화소(8000x5000) 이미지로 쟀다: 이전 구현 574MB(JPEG, PNG 모두) → 지금 JPEG 174MB, PNG 269MB(프로세스 기본 사용량 약 60MB 포함). 컨테이너 한도는 이 값에 맞춰 512m로 둔다(잠정, 배포 후 `docker stats`로 확인).
- 동시 처리 1개. 분석 자리를 5초 안에 얻지 못하거나 호출한 서버가 이미 끊었으면 분석하지 않고 503으로 돌려, 포기한 요청이 자리를 쥐고 줄이 쌓이지 않게 한다.
- 얼굴 개수 제한(기본 10, `RISK_MAX_FACES`)은 risk-lab에서만 한다. 응답의 `faceCount`는 검출한 전체 수다.

## 평가 세트에서 돌려 본 것 (164장, 딥페이크 탐지용 세트)

얼굴 정답 라벨이 없어서 정확도가 아니라 현황이다.

- 얼굴이 하나 이상 검출된 사진 46장(진짜 22, 가짜 24). 이 세트는 얼굴 사진 위주가 아니라 풍경, 음식, 일러스트가 섞여 있다. 그중 16장은 여러 명(최대 18명, 군중 사진).
- 눈으로 6장을 확인했다. 사람 얼굴은 정확히 잡았고, 음식 사진(새우)에서 얼굴 아닌 것을 얼굴로 잡은 오검출이 1건 있었다. 얼굴 크기 중앙값은 39px로 작다(군중 속 얼굴). 오검출률은 측정하지 못했다.
- 얼굴이 검출된 46장의 점수: 품질 중앙값 49.5, 노출도 중앙값 51. GPS가 없다고 보고 낸 종합 점수는 높음 11장, 보통 15장, 낮음 20장(단순 평균이었다면 높음 2장).
- 지연: 중앙값 38ms, p95 97ms(클라우드 CPU).

## 켜는 법

```
docker compose --profile risk up -d --build risk
RISK_ANALYSIS_MODE=http   # 서버 환경 변수. 기본값은 llm
```

CD(`deploy.yml`, `remote-deploy.sh`)에는 아직 연결하지 않았다. 탐지 서비스처럼 CI에서 이미지를 빌드해 올리는 작업이 필요하다.

## 알려진 후속 과제

- `RiskAssessment`의 factors·faces·recommendations가 모두 EAGER `@ElementCollection`이라 얼굴이 10개면 한 번 조회에 수십~백여 행이 조인된다(폴링마다 반복). `@Fetch(SUBSELECT)`나 LAZY가 방법인데, 이 환경에서는 DB를 쓰는 통합 테스트를 돌릴 수 없어 이번에는 바꾸지 않았다.
- 프론트는 실패 사유 `INVALID_IMAGE`에 대한 문구가 필요하다(없으면 일반 안내로 보인다).
